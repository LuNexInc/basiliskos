# Plan — Isolated Codex Desktop App served by Basiliskos (true copy of Codex)

> Planning document. No implementation yet. Mirrors the shipped Basiliskos Claude
> isolation 1:1 so the Codex app behaves the same way: **the real installed Codex
> app, isolated data, routed through the Basiliskos gateway, and updated
> automatically whenever OpenAI ships a new Codex build.**
>
> Companion research (facts, wire contract, community precedent, decision
> points): `docs/CODEX-APP-MULTIMODEL-RESEARCH.md`. Read it first.

## 1. Goal

Charles can click "Open Basiliskos Codex" and get a Codex desktop window that:

- is the **same MSIX package** as his normal ChatGPT/Codex app (so OpenAI
  updates land on it automatically — "true copy of codex");
- runs on an **isolated data home** (`~/.hydra-gateway/codex-profile`) so it
  never touches the normal `~/.codex`;
- talks **only to the Basiliskos gateway** (`http://127.0.0.1:8317/v1`,
  Responses API) which relays to whichever Basiliskos account is active
  (Claude / Grok / Kimi / DeepSeek / Codex);
- is visually distinct (remapped window icon/title) from the normal Codex app;
- follows Basiliskos usage/quota truthfulness rules.

## 2. How Basiliskos Claude isolation works today (the template)

All references are in `src-tauri/src/gateway.rs` unless noted.

1. **Resolve the real app, not a copy** — `installed_claude_exe()`:
   `Get-AppxPackage -Name Claude | Sort Version -Descending | First 1`
   → `%ProgramFiles%\WindowsApps\Claude_<ver>\app\Claude.exe`, verified path.
   Because it resolves the *installed* package each launch, a Store update
   automatically becomes the next Basiliskos Claude.
2. **Isolated data home** — `isolated_claude_profile_dir()` =
   `~/.hydra-gateway/claude-profile`.
3. **Inject the gateway config** — `write_isolated_claude_config(profile, state)`:
   `claude_desktop_config.json` with `deploymentMode: "3p"`,
   `inferenceGatewayBaseUrl: http://127.0.0.1:8317`,
   `inferenceGatewayApiKey: <hydra key>`, `inferenceGatewayAuthScheme:
   "x-api-key"`, `inferenceModels` (the active route's real upstream model
   ids) + `modelDiscoveryEnabled` + `unstableDisableModelVerification`.
4. **Launch the real exe with the isolated data dir** —
   `launch_hydra_claude`: `Command::new(&executable).env("CLAUDE_USER_DATA_DIR",
   &profile)`, stdout/stderr to `profile/Basiliskos Logs/`, kill-on-close job,
   pid tracked, 900 ms startup check, window icon/title remap via
   `claude_window.rs` (`CLAUDE_BASILISKOS_AUMID`,
   `enum_claude_hwnds_for_pid`, icon reapply thread).
5. **Updates** — nothing to build. Same package + Store/auto-updater; the
   isolated data home persists across package updates.

Key isolation enabler: because the app-server control socket, logs, and state
all live under `CODEX_HOME`, a different `CODEX_HOME` gives the isolated
instance its **own app-server** — the same structural property
`CLAUDE_USER_DATA_DIR` gives the Claude window.

## 4. Target architecture (mirror of Claude)

New code (all in `src-tauri/src/`, following existing patterns):

### 4.1 `codex_app.rs` (new module, mirror of `claude_window.rs` + launch)

- `installed_codex_exe()` — `Get-AppxPackage -Name OpenAI.Codex | Sort Version
  -Descending | First 1` → `%ProgramFiles%\WindowsApps\OpenAI.Codex_<ver>\app\ChatGPT.exe`,
  verified (contains `\windowsapps\openai.codex_`, ends `\app\chatgpt.exe`,
  is_file). Sort-by-version gives the update property for free.
- `isolated_codex_home()` — `~/.hydra-gateway/codex-profile` (dir already
  exists from the July prototype; reuse/repair).
- `write_isolated_codex_config(home, state)` — writes:
  ```toml
  # Generated by Basiliskos for the isolated Codex client only.
  # Global ~/.codex is not modified.
  model = "<active route model id>"
  model_provider = "basiliskos"
  model_reasoning_effort = "<route thinking>"
  model_catalog_json = "<home>/model-catalog.json"
  disable_response_storage = true

  [model_providers.basiliskos]
  name = "Basiliskos"
  base_url = "http://127.0.0.1:8317/v1"
  env_key = "BASILISKOS_API_KEY"
  wire_api = "responses"
  stream_idle_timeout_ms = 7200000
  stream_max_retries = 5
  request_max_retries = 4
  ```
  plus `auth.json` seed (`{"OPENAI_API_KEY": null}`) and
  `model-catalog.json` (generated `ModelsResponse`, §4.3).
  The isolated home is fresh, so there is no user `[desktop]` block to merge
  (unlike the shared `~/.codex`). If the home already exists (app ran once),
  **merge**: preserve `[desktop]`, `[plugins.*]`, `[features]`,
  `[marketplaces.*]`, `[mcp_servers.*]` keys the app wrote.
- `launch_hydra_codex_app(app)` — mirror of `launch_hydra_claude`:
  `Command::new(&executable).arg("--user-data-dir=<home>").env("CODEX_HOME",
  &home).env("BASILISKOS_API_KEY", &state.api_key)` — BOTH the Chromium
  profile redirect and the engine home are required for full isolation
  (verified M0: `--user-data-dir` alone creates the second instance; with
  `CODEX_HOME` the engine state also lands in the same isolated home). Logs
  to `home/Basiliskos Logs/`, kill-on-close job, pid in runtime
  (`codex_child`, `codex_job`, `codex_root_pid`, `codex_executable`,
  `codex_home` — names from July commit `5ccd39b6b`), startup check,
  window icon/title remap.
- `stop_hydra_codex_app()` — mirror of `stop_hydra_claude`.
- Window remap: `codex_app.rs` `enum_codex_hwnds_for_pid` (Win32) — the window
  is a Chromium `Chrome_WidgetWin_1`; set a distinct icon (reuse the black-
  icon pattern) + a "Basiliskos Codex" title so it is not confused with the
  normal app.

### 4.2 Front-proxy Codex dial (gateway.rs, prior art exists)

The client sends `model = "<route model>"` (from config.toml) to
`/v1/responses`. CLIProxyAPI routes by model name to a credential's model
list, so the request must be rewritten to the **active route's real upstream
model id** before relay — exactly what `rewrite_claude_request` does for
`/v1/messages`, and exactly what the July commit `5ccd39b6b` did for
`/v1/responses` + `/v1/chat/completions` (removed later; recover from git).

Scope: extend the existing rewrite path to also handle `/v1/responses`
(keep `/v1/messages` untouched for the Claude dial):
- rewrite `model` → active route model (honor a client-chosen model id like
  the Claude path does);
- apply the same client fixups on the Responses shape (kimi flatten,
  deepseek placeholder, xai web_search strip);
- leave `store`/`reasoning`/`tools` passthrough to CLIProxyAPI (it speaks
  Responses upstream: README "any OpenAI (including Responses) client",
  `codex:` config section with `optimize-multi-agent-v2`,
  `disable-codex-cloaking`).

### 4.3 Model catalog (the picker must show Basiliskos models)

Codex's `/models` discovery expects the internal `ModelInfo` schema, not the
standard OpenAI list (openai/codex#37122). Two options, decide in M2:

- **A (recommended): generate `model-catalog.json`** in the isolated home —
  a `ModelsResponse` (`{"object":"list","data":[ModelInfo,...]}`) with one
  `ModelInfo` per Basiliskos route model (slug = real upstream id,
  display_name, supported reasoning levels, shell_type, base_instructions,
  truncation_policy, tool types — copy field shapes from a known-good catalog
  from the openai/codex source fixtures; validate with the bundled
  `codex.exe`). `model_catalog_json` in config.toml points at it.
- B: serve the internal schema from the front proxy at `/v1/models` for
  codex-provider requests. Cleaner long-term; tracks #37122.

### 4.4 Account + model switching

- Route selection: per-client state (`active_codex_account`,
  `codex_routes`) from the July commit — Codex dial independent of the
  Claude dial.
- Model change = rewrite `model` in the isolated config.toml + the user
  starts a NEW session (model is pinned per session in `state_5.sqlite`;
  openai/codex#15364, #29160). The UI shows a "Codex needs a new session /
  restart for the model change" hint.

### 4.5 Anchored account (DECISION 1 = b, confirmed by Charles)

The isolated app carries ONE real ChatGPT credential so mobile/remote and
cloud features have an OpenAI identity, while inference routes through
Basiliskos. This is the "phone anchor" pattern from
VallierDev/codex-switcher applied to the isolated home.

- **The anchor lives IN the Basiliskos vault (confirmed 2026-08-12):** the
  anchor is a MARKED relay account in `~/.hydra-gateway/gateway/auth/` (a
  normal `codex-*.json` with an `anchored` marker). Basiliskos is Charles's
  OAuth vault — the isolated `auth.json` is a *projection* of the vault, the
  same proven pattern as `codex_cli.rs` (seed via `translate_codex_cred`,
  capture-back via `capture_live_codex_credential_if_known`). No second
  credential store.
- **One refresher per credential (hard rule):** the app owns the live
  refresh (it is a real login); the relay's automatic codex refresh loops
  MUST exclude the anchored account; the relay only capture-backs changes
  into the vault. Two refreshers on one refresh token invalidate each other.
- **The anchor is an identity, not a route:** route switching never touches
  the anchor projection — disk stays pinned, proxy exit switches. The
  anchor MAY also be selectable as an inference account, but does not have
  to be.
- **Usage synergy:** the anchor's ChatGPT quota is already tracked by
  Basiliskos usage machinery — the isolated app's cloud/mobile usage shows
  in the panel.
- **Seed/fallback:** seed from the vault; if M0 shows the MSIX app ignores a
  pre-seeded auth.json, establish the anchor with one real OAuth login
  inside the isolated app, then vault it.
- **Provider auth stays separate:** `model_provider = "basiliskos"` +
  `env_key = "BASILISKOS_API_KEY"`; `requires_openai_auth` stays unset so
  the provider uses the Basiliskos bearer, not the ChatGPT tokens.

## 5. Milestones (stop + get approval after each, per AGENTS.md)

### M0 — Verification spikes (no product code; nothing touches real ~/.codex)

**M0 RESULTS (2026-08-12, run live):**

1. **CODEX_HOME honored at the engine level — CONFIRMED.** The installed
   `codex.exe` read config/auth/state entirely from a throwaway `CODEX_HOME`
   (probe evidence: config error referenced the temp home; `~/.codex`
   untouched — mtimes unchanged).
2. **Two instances — POSSIBLE via `--user-data-dir` (M0 re-test, corrected).**
   An earlier "impossible" conclusion was wrong: the first test never passed
   the flag (PS 5.1 `ArgumentList` is null — `InvokeMethodOnNull`), so the
   app launched plain and hit the global lock ("Opening in existing browser
   session", exit 0). Re-tested with `$psi.Arguments = '--user-data-dir="<isolated>"'`
   + `CODEX_HOME=<isolated>`: the second instance STARTED and ran (8 new
   ChatGPT processes, alive >15s, full Chromium profile + codex engine state
   initialized under the isolated home), while the normal app (20 processes)
   and `~/.codex` (mtimes unchanged) were untouched. **The global lock is
   scoped by the Chromium user-data dir, and `--user-data-dir` redirects it.**
   Design consequence: launch with BOTH `--user-data-dir=<isolated home>` AND
   env `CODEX_HOME=<isolated home>` — coexistence works, no "close the normal
   app" mode needed. (Re-verify on each Codex app update: a future build
   could scope its lock differently; keep the close-first flow as a fallback.)
3. **App-session-to-relay test — DEFERRED to M1** (needs the normal app
   closed so the isolated app can run).
4. **`model_catalog_json` — CONFIRMED.** Installed `codex.exe` with a
   throwaway `CODEX_HOME` + bad catalog file failed with `failed to parse
   model_catalog_json path ... as JSON: missing field 'models'`. The
   mechanism is live and the file schema is `{"models": [ModelInfo...]}`
   (NOT the `{"object":"list","data":[...]}` wire shape).
5. **`/v1/responses` relay — CONFIRMED LIVE, ZERO code changes.** The live
   front proxy (Bearer auth) → CLIProxyAPI → DeepSeek route returned a
   correct Responses response (non-stream HTTP 200 in 1.0s; SSE stream with
   `response.created` / `response.in_progress` / `response.output_item.added`
   events, HTTP 200). The Codex wire protocol already works through the
   gateway today. Per-provider coverage (kimi/grok/claude routes) deferred to
   M2 (route-switch testing would disturb the live controller state).
6. **Anchored auth — DEFERRED to M1** (needs the isolated app running).

## 6. Decision points for Charles

1. **Auth identity of the isolated app — DECIDED (b) anchored account**
   (§4.5): one real ChatGPT credential in the isolated `auth.json` for
   mobile/remote + cloud features; inference via Basiliskos. Remaining
   sub-choice: which relay account anchors the app (default: main codex
   relay account).
2. **Desktop app only, or also the CLI** (`launch_hydra_codex` CLI variant
   from July)? Recommend app first (this plan), CLI later if wanted.
3. **Single-instance tradeoff — RESOLVED at M0.** Two instances coexist via
   `--user-data-dir=<isolated home>` (the lock is scoped by the Chromium
   user-data dir). No "close the normal app" mode required; keep it as a
   fallback only if a future Codex update re-scopes the lock.
3. **Catalog option A (generated file) vs B (serve internal schema)** —
   recommend A for M1..M3, revisit B when the front proxy stabilizes.
4. **Scope of model switching**: config rewrite + new-session hint (whole
   ecosystem does this) vs trying `state_5.sqlite` surgery (fragile, not
   recommended).
5. **Naming/identity**: window title "Basiliskos Codex", distinct icon.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| MSIX app ignores `CODEX_HOME` at startup | **RESOLVED (M0): engine honors CODEX_HOME; app-level verified once the normal app is closed (M1)** |
| Single-instance lock — **RESOLVED at M0** | The global lock is scoped by the Chromium user-data dir; passing `--user-data-dir=<isolated home>` (with `CODEX_HOME`) starts a fully independent second instance (verified: 8 new processes, own Chromium profile + engine state, normal app + `~/.codex` untouched). Keep the close-first flow as a fallback if a future app update re-scopes the lock |
| Two instances share MSIX LocalCache (WebView2/leveldb) | Same spike #2; if leveldb locks conflict, log-only damage; keep user state out of LocalCache |
| Anchor token rotation: the app AND the relay both refresh the same account; rotated refresh tokens can invalidate each other | Anchor a dedicated account the relay treats as read-only, OR let the app own refresh and the relay only capture-back. Never run two concurrent refreshers on the same credential |
| Remote "cloud" tasks bypass Basiliskos (run on OpenAI servers with anchor quota); only LOCAL sessions route through it | Document in UI: remote sessions route via Basiliskos only when they run locally; cloud-mode tasks use the anchor's ChatGPT quota |
| App may store auth in its own secure store, ignoring seeded auth.json | M0 spike #6; fallback one-time real OAuth login inside the isolated app |
| App-server daemon conflict on shared socket | Socket is under `$CODEX_HOME/app-server-control` → separate homes = separate sockets (verified in asar). Also confirm the app-server child dies on kill (job tree) |
| Model picker empty for custom provider | `model_catalog_json` (M3); validate with bundled codex.exe |
| Client picks an OpenAI model from the backend list (logged-in anchor) | The dial is a REAL model switcher (decision 2026-08-13): CLIProxyAPI routes the picked model id to its own provider (grok-4.x → xAI, gpt-5.6-* → Codex, kimi-k3 → Kimi, deepseek-* → the compat block), so inference follows the picked model, not the active route. One account per provider stays enabled; the active account drives the Claude path only |
| Existing sessions pin old model (#29160) | New-session hint; never rewrite the user's real `~/.codex` |
| ModelInfo `base_instructions` required — missing it degrades agent behavior (#37122) | Vendor the system prompt from the openai/codex `prompt.md` (or the app's bundled catalog) into each generated ModelInfo |
| CLIProxyAPI Responses translation gaps per provider | M0 spike #5 live smoke; fixups like the Claude path |
| App updates mid-session | Same package as normal app; next Basiliskos launch uses the new build (property required by Charles, inherent to this design) |
| Secrets: hydra key in the isolated home | Same local-only key as the Claude config; keep out of logs (`check-runtime-log-secrets.ps1`) |
| July `codex-profile` already exists with stale config/auth | M1 reconciles/repairs it (fresh seed) before first launch |
